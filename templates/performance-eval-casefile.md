# 绩效评价 AI 员工
> 一个基于证据的绩效评价 AI 员工。

**领域:** 人力资源 / 组织运营  ·  **状态:** 公开参考案例

## 业务问题

绩效评价依赖管理者的记忆与印象。本应支撑评级的证据——OKR、一对一记录、项目记录、同事反馈——分散在各个系统里，很少在评议会之前被汇总。

### 为什么现有流程会失败

管理者在时间压力下无法回想起每一条证据，于是评价塌缩成一个与事实脱钩的分数。同一个人一次性完成“发生了什么”和“这意味着什么”，把观察与判断混在一起，引入了偏差与不一致。

## 我如何重构这项工作

把证据与评价分离开。将工作重构为由一名 AI 员工协同完成的三个步骤：先提取这个人实际做了什么的事实，再把这些事实映射到绩效标准，最后才形成反馈。管理者拿到的不是一纸判决，而是一份有出处、结构化的草稿，供其确认或纠正。

### AI 员工定义

- **角色:** 绩效评价专员
- **职责:**
  - 在做出任何判断之前先把证据汇总
  - 把事实提取与标准映射同打分分开
  - 产出有出处、可供管理者信任与编辑的草稿
- **任务:**
  - 从已连接系统收集证据
  - 提取关于“做了什么”的事实性陈述
  - 把每条事实映射到相关绩效标准
  - 依据事实加标准形成反馈
  - 起草可供人工确认的评议稿

## 业务语义

语义层是这个案例的全部重点。只有当“发生了什么”作为与“这意味着什么”不同的对象存在时，评价才变得公平且可审计。语义定义了标准、证据类型，以及把它们连接起来的映射规则。

| 层 | 捕获什么 |
|---|---|
| 标准本体 Standards Ontology | 绩效维度、等级与行为锚点 |
| 证据类型 Evidence Types | OKR、一对一记录、项目记录、同事反馈及其出处 |
| 映射规则 Mapping Rules | 哪些证据支撑哪些标准，以及支撑强度 |

## Agent 架构

证据与评价被放在不同的 Agent 中，以使任何一步都无法悄悄把观察与判断合并。在管理者看到任何内容之前，审查器会先检查“事实→标准”的映射。

| Agent | 角色 | 输入 | 输出 |
|---|---|---|---|
| 证据收集器 Evidence Collector | 从各系统收集原始证据 | 已连接系统 | 原始证据 |
| 事实提取器 Fact Extractor | 把证据转为事实性陈述 | 原始证据 | 事实清单 |
| 标准映射器 Standard Mapper | 把事实链接到标准 | 事实 + 标准 | 已映射事实 |
| 评价器 Evaluator | 依据已映射事实形成反馈 | 已映射事实 | 评议草稿 |
| 审查器 Reviewer | 校验映射质量 | 评议草稿 | 已审查草稿 |

**工作流:** 证据收集器 → 事实提取器 → 标准映射器 → 评价器 → 审查器 → 管理者确认 → 最终评议

## 约束框架

约束框架强制执行使本案例可信的那种分离：事实不能被跳过，没有映射好的证据就不会产出任何评级。

- **上下文:** 已连接的 HR 系统、OKR 记录、一对一记录、同事反馈
- **工具:** 证据源的只读连接器、标准查询
- **规则:** 每个评级都必须追溯到一条已映射事实；事实必须有出处
- **护栏:** 对源系统只读；绝不自动定稿评级
- **人在环:** 管理者在草稿成为正式记录之前确认或纠正

## 评估

在同样的案例上，把 AI 员工的有出处草稿与管理者的手写评议做对比；检查每个评级是否都能追溯到证据，以及管理者是否只需很少修改就能接受草稿。

| 指标 | 目标 |
|---|---|
| 证据可追溯性 | 100% 评级链接到出处 |
| 管理者编辑距离 | 草稿以 < 20% 修改被接受 |

**人工复核:** 管理者确认最终评议
